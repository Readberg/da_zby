# WORKFLOW — как мы работаем

## 1. Общий цикл

```
идея → задача в Jira (Бэклог / К выполнению) → В работе (ветка от dev)
→ код + автотесты + доки → PR в dev (Claude мержит сам при зелёных проверках)
→ автотесты в CI зелёные → Готово (Claude) — или Тестирование, если есть ключевые 🔑 кейсы → Готово (владелец)
→ накопили на релиз → PR dev → main, тег, CHANGELOG
```

Правило: **сначала задача — потом код.** Исключение — опечатки в доках.
Правило №1 — **не ломать работающую логику** (см. `CLAUDE.md`). Правило №2 — **у каждой задачи есть тест-кейсы, и всё, что можно, автоматизировано** (D-046); вручную владелец проверяет только ключевое (🔑).

## 2. Jira

- Сайт `fmlight.atlassian.net`, проект **DAZBY**; инструменты — Atlassian MCP (`getAccessibleAtlassianResources` → `cloudId`; `createJiraIssue`, `editJiraIssue`, `addCommentToJiraIssue`, `getTransitionsForJiraIssue` + `transitionJiraIssue`). Названия переходов не угадывай — запрашивай. Токены в файлы и комментарии не писать.
- Язык — русский. Названия коротко и по делу («Форма входа по email»).

### Типы

| Тип | Когда |
|---|---|
| Эпик | Крупный блок (см. `ROADMAP.md`) |
| Задача | Конкретная работа с проверяемым результатом |
| Баг | Работает не так, как в доках |
| Анализ | Идея/вопрос «на подумать» и **ключевое решение**, требующее согласования. Код по нему не пишется, пока владелец не решил |

### Статусы

`Бэклог → К выполнению → В работе → Тестирование → Готово`

- **Бэклог** — отложенное и идеи; на доске не показывается.
- **К выполнению** — решено делать в ближайшее время.
- **В работе** — ведётся сейчас.
- **Тестирование** — реализовано, влито в `dev`, CI зелёный, **идёт приёмка Claude** (D-097). Остаётся здесь, только если нужна проверка, которую Claude сделать не может (см. ниже).
- **Готово** — все тест-кейсы пройдены: автотестами в CI и приёмкой Claude на стенде (ставит Claude).

### Кто тестирует (D-097)

Тестирование и приёмку ведёт Claude, владельца к ним не привлекают. Для каждой задачи в «Тестировании» Claude: гоняет автотесты и CI; проверяет изменённое на стенде (браузер на 360 и 1280 px, API, ответы сервера, логи); прогоняет 🔑-кейсы настолько, насколько их можно выполнить без чужого аккаунта и телефона; пишет в Jira комментарий «что проверено, как, результат»; закрывает задачу «Готово». Найденный баг чинит сам.

Владельцу уходит **только то, что Claude физически не может проверить**: приложение Telegram и превью ссылок на телефоне, вход в чужой аккаунт или дашборд (Umami), вкусовая оценка вида. Такие пункты Claude собирает в итоговую сводку явным списком «не проверено и почему», а задача не остаётся висеть: Claude закрывает её с пометкой «не проверено: …», кроме случаев, когда риск высокий (права, необратимые действия, деньги) — тогда задача остаётся в «Тестировании».

### Что считается 🔑, а что — 🤖

🔑 вручную — только то, что автотест не подтвердит или где решает вкус и риск:
- внешний вид и удобство **ключевых экранов** (главная, прогнозы, рейтинг, профиль, админка) на телефоне и десктопе;
- реальные внешние интеграции, которые в CI замоканы: письма входа, Google/Telegram-вход, превью ссылок в мессенджерах, выкладка на Railway/прод;
- права и роли на живых данных (первый админ, «чужой не может»), необратимые действия (закрытие сезона, удаление);
- то, что владелец явно пометил 🔑.

🤖 автотестами — всё остальное: API-контракты, валидация, ошибки, вёрстка без переполнения на 360/1280, цели касания и фокус, отсутствие секретов в бандле, правила очков и дедлайнов (unit + SQL-тесты), кеш и запасные ветки. Автотест должен проверять то же, что ручной кейс, иначе кейс остаётся 🔑.
- Нашёл баг при проверке → владелец пишет в комментарии/заводит «Баг»; задача возвращается в «В работе» или остаётся в «Тестировании» до исправления.

### Описание задачи (шаблон, минималистично)

```
**Что:** что делаем (1–2 строки)
**Зачем:** какую ценность даёт
**Почему так:** почему выбран этот подход (и что отвергли, если важно)
**Как:** ключевые шаги
**Результат:** критерии готовности (2–5 пунктов)
**Тест-кейсы (🤖 — автотест: файл; 🔑 — ключевая ручная проверка):**
1. Предусловие: … Шаги: … Ожидаемо: …
2. …
```

Требования к тест-кейсам: исполнимы владельцем без знания кода (команды, адреса, кнопки названы точно); у каждого проверяемый результат; покрывают роли (гость/пользователь/админ), мобильную ширину 360 px, граничные случаи и «не сломалось ли старое» (ссылка на 1–2 связанные работающие функции). Без «проверить, что работает».

### Метки

`frontend` **или** `backend` (ровно одна из них у каждой Задачи), плюс по смыслу: `db`, `auth`, `design`, `docs`, `devops`, `analytics`, `api`. У багов — `bug` и по возможности `frontend`/`backend`.

### Комментарии — только по ключевым изменениям, кратко

- `▶ Старт:` что беру в работу, ветка.
- `✔ Сделано:` что изменено (1–3 пункта), PR.
- `⚖ Решение:` принятое решение и причина (дубль в `DECISIONS.md`).
- `⛔ Блокер:` что мешает и что нужно от владельца.
- `❓ Вопрос владельцу:` ключевое решение с вариантами.

### Переходы

1. Взял → ветка → «В работе» + `▶ Старт`.
2. PR влит в `dev`, CI зелёный → тест-кейсы актуализированы и помечены 🤖/🔑 → `✔ Сделано` → все 🤖: «Готово»; есть 🔑: «Тестирование».
3. Владелец прошёл 🔑-кейсы → «Готово».
4. Побочная идея/проблема → новая «Анализ»/«Баг» в «Бэклог», текущую работу не расширять.

### Доска (настраивается владельцем один раз — `SETUP.md`)

Колонки: К выполнению · В работе · Тестирование · Готово. Дорожки: Frontend · Backend · Баги.

## 3. Ключевые решения

Что считается ключевым — в `CLAUDE.md`. Алгоритм:
1. Заведи «Анализ»: проблема → варианты → цена и риски каждого → **твоя рекомендация** (честно, с аргументами; стиль `ADVISOR.md`).
2. Спроси владельца (в диалоге — AskUserQuestion; без владельца — в итоговой сводке). Не блокируй независимую работу.
3. После ответа: запись в `DECISIONS.md` (✅), решение в Jira, затем реализация.

## 4. Git

- `main` — стабильное состояние. `dev` — интеграция.
- Рабочие ветки от `dev`: `feat/DAZBY-12-magic-link`, `fix/…`, `chore/…`, `docs/…`.
- Коммиты — Conventional Commits на английском: `feat|fix|docs|chore|refactor|test|perf|build(scope): summary (DAZBY-12)`. Маленькие и осмысленные.
- PR в `dev`: заголовок как коммит; описание: что и зачем · как проверить · **Риск регресса** · миграции/доки · ссылка на задачу. Squash-мерж, ветку удалить.
- Прямые пуши в `main` запрещены; релизный мерж `dev → main` — через PR.
- Миграции БД — отдельный коммит, в PR отметка «есть миграция».

## 5. Версии и релизы

`X.Y.Z`: **X** — крупный, масштабный релиз (публичный запуск = `1.0.0`); **Y** — средний релиз с важной функциональностью; **Z** — мелкие правки и доработки. До публичного запуска `0.Y.Z`.

**Одной командой (D-085):** `pnpm release <patch|minor|major> --title "название" --task DAZBY-N` (сначала `--dry-run`; при недоступных GitHub Actions — флаг `--local-checks` после полного локального прогона, D-108). Скрипт сам делает пункты 2, 4 и 5: ветка с версией и CHANGELOG → PR в `dev` → ждёт зелёный CI → мерж → PR `dev` → `main` → мерж-коммит → тег → GitHub Release с текстом из CHANGELOG → проверка стенда. Если деплой Railway упал, скрипт запускает его заново (до трёх раз, D-092). Красный CI останавливает релиз; пустой раздел «Не выпущено» — тоже. Пункты 1, 3, 6 и 7 остаются на мне вручную.

Чек-лист релиза:
1. В `dev` нужные задачи в «Тестирование» (или «Готово»); `lint typecheck test build` и e2e smoke зелёные.
2. `CHANGELOG.md` (новый раздел сверху) и версия в `package.json`.
3. Доки актуальны (`PRODUCT`, `API`, `DATA_MODEL`, `DESIGN`, `DECISIONS`).
4. PR `dev` → `main` (merge commit), заголовок `release: vX.Y.Z`.
5. Тег `vX.Y.Z`; GitHub Release с текстом из CHANGELOG.
6. Миграции на прод (когда появится) — отдельным шагом до выкладки кода.
7. Jira: комментарий «Релиз vX.Y.Z» в эпиках.

`CHANGELOG.md` — Keep a Changelog, на русском: Добавлено · Изменено · Исправлено · Удалено · Миграции БД · API (изменения и устаревания). У записи — ключ Jira.

## 6. Definition of Done

- [ ] выполнены критерии «Результат»; **правило №1 соблюдено**, в PR заполнен «Риск регресса»;
- [ ] `lint`, `typecheck`, `test`, `build` зелёные; для логики и API — тесты (unit/contract), для ключевых сценариев — e2e;
- [ ] мобильная ширина 360 px и десктоп проверены; состояния загрузки/пусто/ошибка есть;
- [ ] права проверены (гость/пользователь/админ), RLS не обойти;
- [ ] доки обновлены; новые ключевые UI-элементы добавлены в библиотеку `docs/design/`;
- [ ] нет секретов и лишних файлов;
- [ ] в Jira: актуальные метки, тест-кейсы с пометками 🤖/🔑, комментарий `✔ Сделано`, статус «Готово» (всё 🤖) или «Тестирование» (есть 🔑).

## 7. Общение с владельцем

- Вопросы — одним списком; не засыпать мелочами.
- Ключевые решения — только после согласования.
- Финал задачи/запуска: что сделано · что проверить (ссылка на тест-кейсы) · честная оценка рисков · что дальше.
