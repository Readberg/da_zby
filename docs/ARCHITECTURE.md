# ARCHITECTURE — как устроен код

## Принципы

1. **Не ломать работающее.** Любое изменение существующего поведения — сначала тесты на текущее поведение, затем правка; минимальные диффы.
2. **БД — источник истины для правил.** Дедлайны, очки, роли обеспечивает Postgres (RLS, триггеры, функции). Фронтенд дублирует правила только для UX.
3. **Контракт прежде всего.** Фронтенд и внешние клиенты общаются с бэкендом через версионируемый внутренний API (`docs/API.md`); логика — в сервисном слое.
4. **Типобезопасность end-to-end.** Типы БД генерируются, входы валидирует Zod, DTO типизированы.
5. **Просто и читаемо.** Без лишних абстракций и зависимостей, без «на вырост» кода без задачи.

## Общие помощники (D-071)
- `src/lib/search-params.ts` — `firstParam`: параметр адреса как одна строка.
- `src/lib/form-errors.ts` — `fieldErrorsFromIssues`: ошибки Zod → ошибки полей формы.
- `src/server/services/pg-errors.ts` — коды SQLSTATE (`UNIQUE_VIOLATION`, `FOREIGN_KEY_VIOLATION`, `CHECK_VIOLATION`), которые сервисы превращают в проблемы API.
- Новый код, которому нужно то же самое, использует их, а не копирует.

## Поток данных

- **Чтение страниц (RSC):** страница вызывает сервис напрямую (`src/server/services`) — без HTTP-прыжка.
- **Мутации и клиентские запросы:** через `/api/v1/...` типизированным клиентом `api-client.ts`.
- **Исключения:** вход (Supabase Auth) и загрузка файлов в Storage идут напрямую под RLS.
- **Server Actions** для доменных операций не используются (решение D-038), чтобы у логики был один вход — API.
- Сервис получает Supabase-клиент **пользователя**; secret-ключ — только в `server-only` модулях и только для операций, невозможных под RLS.

## Аутентификация

- `@supabase/ssr`, сессия в cookie, `middleware.ts` обновляет токен.
- Серверные проверки — `supabase.auth.getUser()`, не `getSession()`.
- Единственный способ входа — Telegram через бота (D-054, D-056). Кнопка вызывает `POST /api/v1/auth/telegram/start`: сервер создаёт одноразовую попытку (`login_tokens`, хранится только SHA-256 токена, 10 минут) и возвращает ссылку `tg://resolve?domain=<бот>&start=<токен>` и двузначное число. Страница открывает приложение Telegram, пользователь нажимает Start, бот присылает три числа, нужно выбрать то, что на сайте (защита от входа чужого браузера по пересланной ссылке; одна попытка). Страница опрашивает `GET /api/v1/auth/telegram/status` и при `confirmed` переходит на `/auth/telegram?token=…`: сервер гасит токен (один раз), находит или создаёт пользователя через Admin API (синтетическая подтверждённая почта `tg<id>@telegram.invalid`), получает токен `generateLink` и обменивает его на сессию `verifyOtp` обычным серверным клиентом (cookie).
- Вебхук бота — `POST /api/telegram/webhook`, защищён секретом, выведенным из токена бота (`X-Telegram-Bot-Api-Secret-Token`); при старте сервера `instrumentation.ts` сам направляет вебхук на адрес сайта (только в production, не на localhost). Используется активный аккаунт приложения Telegram, поэтому смена аккаунта в Telegram работает. Домен для @BotFather не нужен.
- Путь возврата передаётся cookie `login_next` и перепроверяется `safeRedirectPath`; редиректы строятся от публичного адреса (`publicOrigin`).
- `/auth/confirm` (по token_hash) остался служебным: через него e2e-тесты входят тестовым пользователем (DAZBY-52).
- Нужны серверные секреты `TELEGRAM_BOT_TOKEN` и `SUPABASE_SECRET_KEY`; без любого из них вход и вебхук закрыты (fail closed). Таблица `login_tokens` доступна только ключу сервиса.
- `profiles.nickname IS NULL` → `/onboarding` (кроме выхода и статики).
- Админ: `requireAdmin()` в layout `/admin` (гость → вход, не админ → «Нет доступа») + RLS + уровень `admin` в `withApi` (`is_admin()`). Ссылка «Админка» в шапке видна только админам.
- Админы: Telegram-id из `TELEGRAM_ADMIN_IDS` перед созданием аккаунта записываются в `admin_bootstrap` (по синтетической почте) — дальше срабатывает существующий триггер (миграция `…000100`).

## Кеширование

- Рейтинг и статистика (`rating.cached.ts`): `'use cache'` + `cacheLife` (свежесть 5 минут, обновление раз в 30, срок 24 часа) и тег `rating`; читают анонимным клиентом без cookie (`createAnonClient`). Админские маршруты после мутаций вызывают `invalidateRating()` (`revalidateTag(…, { expire: 0 })`).

| Данные | Стратегия |
|---|---|
| Видео YouTube | кеш в памяти процесса 1 ч + последний удачный список при сбое (`src/server/services/videos.ts`, D-045) |
| Рейтинги, публичные профили | `revalidate = 1800`; таблица тура до дедлайна — не дольше, чем до дедлайна (чужие прогнозы открываются в дедлайн, D-084) |
| Справочники (турниры, клубы, туры) | `revalidate = 300` + `revalidateTag` при изменении |
| Свои прогнозы, свой профиль, админка | без кеша |

После внесения результата матча — `revalidateTag`, чтобы очки не ждали 30 минут.

## Безопасность

Проверка прав на реальной БД — `tests/e2e/permissions.spec.ts` (гость / участник / админ); заголовки — `src/config/security-headers.ts` (D-074).

- Секреты только на сервере (`server-only`), валидация env на старте.
- Все входы валидируются Zod; права проверяются на сервере и в RLS.
- Загрузки: проверка типа и размера на клиенте и сервере; аватары в `avatars/<user_id>/…`.
- Заголовки безопасности и CSP в `next.config` (разрешить YouTube-nocookie, Supabase, картинки Storage).
- Внешние API (города) — только через серверный маршрут с кешем, таймаутом и запасным вариантом.
- Не логировать токены, email, персональные данные.

## Страны и города

Страны — статический список ISO 3166-1 с русскими названиями (в БД `country_code`). Города — публичный геокодер через серверный прокси с кешем и свободным вводом как запасным вариантом; выбор сервиса — ключевое решение (согласовать).

## Время

БД — `timestamptz` (UTC); профиль — `utc_offset_minutes` (180 по умолчанию). Любой показ и ввод времени — через `src/lib/time.ts`. Админ вводит время матчей в своём поясе, хранится UTC.

## Тесты

Качество поверх обычных тестов (D-078): доступность — `tests/e2e/a11y*.spec.ts` (axe), клавиатура и reduced-motion — `keyboard.spec.ts`, бюджеты — `performance.spec.ts`, объём — `pnpm perf:scale`.

- **Unit (Vitest):** `scoring.ts`, `time.ts`, парсинг RSS, фабрики.
- **Contract (Vitest):** каждый эндпоинт API v1 — успех и ошибки по схеме; права для гостя/пользователя/админа.
- **SQL-сценарии:** RLS и триггеры (дедлайн, подсчёт, запрет самоповышения роли, bootstrap админа) — скрипты в `supabase/tests/`.
- **E2E (Playwright, smoke):** главная; вход (тестовый пользователь через Admin API); прогноз; рейтинг; админ вносит результат.
- Внешние сервисы в автотестах — только моки/фикстуры.
- Ручное тестирование владельцем — по тест-кейсам из Jira; оно дополняет, а не заменяет автотесты.
- CI (GitHub Actions) на PR: lint, typecheck, test, build, e2e smoke.

## Производительность

`next/image`, `next/font` (cyrillic, latin), ленивый плеер, индексы в миграциях, рейтинги через представления. Для ~1000 уникальных в месяц ничего тяжелее не нужно.

## Деплой

Railway после базовой разработки: сборка `pnpm build`, запуск `pnpm start`, переменные в Railway. Прод-Supabase — отдельный проект; миграции те же файлы; ключи другие.

## Языки (D-088)

- Страницы — в `src/app/[locale]/…` (`ru`, `en`); `src/proxy.ts` по cookie `lang` переписывает адрес (`/rating` → `/en/rating`), посетитель видит прежний адрес. Логика — `src/i18n/routing.ts` (чистая, с тестами); адрес с языком в начале перенаправляется на обычный; `/admin` всегда русский; `/api`, `/auth` не затрагиваются.
- `<html lang>` ставит `src/app/[locale]/layout.tsx`; оба языка известны на сборке (`generateStaticParams`), поэтому статичная оболочка есть у каждого.
- В клиентском коде вместо `usePathname()` — `useAppPathname()` из `src/i18n/use-app-pathname.ts`: он возвращает адрес без языкового сегмента.
- Картинки превью (`opengraph-image.tsx`) — обработчики маршрутов: у них нет общего хранилища запроса, поэтому язык берётся из `dictionaries[locale]`, а не из `getMessages()`; прокси пропускает такие адреса без редиректа.
- Админка вне перевода: тексты `ru.admin` остаются русскими.
