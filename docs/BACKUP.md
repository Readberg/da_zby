# BACKUP — резервные копии базы и восстановление

Решение: D-089. Сайт и его база — одно окружение (D-080), на бесплатном плане Supabase копий нет, поэтому копии делает GitHub.

## Что копируется

Каждую ночь (02:17 UTC) и по кнопке workflow `db-backup` делает выгрузку проекта `ksykaqwkbfqtkvdxqedv`:

| Файл | Что внутри |
|---|---|
| `schema.sql` | схема `public`: таблицы, ограничения, функции, триггеры, политики RLS, представления |
| `data.sql` | данные: все таблицы `public` (клубы, турниры, сезоны, туры, матчи, прогнозы, профили, личные данные профилей), аккаунты входа `auth` (в т. ч. `auth.users`) и индекс файлов `storage.objects` |
| `TAKEN_AT` | время выгрузки |

Копия — приватный артефакт `dazby-backup` на странице запуска (Actions → db-backup → запуск → Artifacts), хранится **30 дней**. Скачать могут только участники репозитория. В файлах **персональные данные** (почта, Telegram-id, ники): не пересылайте и не выкладывайте их.

**Не копируются:** сами файлы из хранилища (фото участников `avatars`, логотипы клубов `club-logos`) — только их список. Логотипы клубов загружаются из админки заново; фото участники загрузят заново. Если файлы понадобятся — скажите, добавлю выгрузку хранилища отдельной задачей.

Проверка внутри workflow: файл не пустой и в нём есть `profiles`, `tournaments`, `seasons`, `clubs`, `tours`, `matches`, `predictions` и `auth.users`. Если что-то пропало, запуск красный и GitHub присылает письмо «workflow failed».

## Как проверить, что копии есть

GitHub → репозиторий → **Actions → db-backup**: по запуску на каждый день, зелёная галочка и артефакт `dazby-backup` внизу страницы запуска.

## Как восстановить

Восстанавливать лучше **в новый пустой проект Supabase**, а не поверх живого, и только потом переключать сайт.

1. Создайте проект Supabase (регион Frankfurt), в Settings → Database возьмите строку подключения (`postgresql://postgres:<пароль>@db.<ref>.supabase.co:5432/postgres`).
2. Скачайте артефакт, распакуйте (`tar -xzf dazby-backup-ГГГГ-ММ-ДД.tar.gz`).
3. Примените схему, затем данные (нужен `psql`):
   ```bash
   psql "$DB_URL" -f backup/schema.sql
   psql "$DB_URL" -f backup/data.sql
   ```
   `data.sql` начинается с `SET session_replication_role = replica`: триггеры и внешние ключи при загрузке не мешают, очки не пересчитываются.
4. Создайте в проекте бакеты `avatars` и `club-logos` (публичные) — как в миграциях — и загрузите логотипы клубов заново из админки.
5. Переключите сайт: в Railway поменяйте `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`, `SUPABASE_SECRET_KEY`, а в GitHub — `SUPABASE_ACCESS_TOKEN`/`SUPABASE_DB_PASSWORD` и `PROJECT_REF` в workflow (`db-migrate`, `db-backup`).
6. Проверьте `/api/v1/health/strict`, вход через Telegram и рейтинг.

**Честно:** полный порядок восстановления в новый проект ещё **не отрепетирован** (в CI нет Docker/локального Supabase; сама выгрузка проверена). Рекомендую один раз отрепетировать на пустом тестовом проекте до того, как копия понадобится по-настоящему, и поправить этот файл по результатам.

## Если копии перестали делаться

Самая частая причина — истёк токен `SUPABASE_ACCESS_TOKEN` (Settings → Secrets and variables → Actions). Обновите его и запустите workflow вручную.
