### T-E1-01 · Инициализация проекта · `frontend` `devops`
**Что:** создать приложение Next.js (App Router) на TypeScript `strict`, Tailwind, pnpm; структура `src/` по `CLAUDE.md`.
**Зачем:** база, на которой строится всё остальное.
**Почему так:** актуальный стандарт стека, один репозиторий, бесплатный деплой.
**Как:** `create-next-app` в корне репозитория без затирания существующих файлов; `.nvmrc`, `engines`, пакет `da-zby`, корневой `README.md` (запуск за 5 команд).
**Результат:** проект запускается, собирается, TypeScript строгий.
**Тест-кейсы:**
1. `pnpm install && pnpm dev` → открыть `http://localhost:3000` → страница открывается без ошибок в консоли браузера.
2. `pnpm build` → завершается без ошибок.
3. В `tsconfig.json` включён `strict`.

### T-E1-02 · Контроль качества и тесты · `devops` `backend`
**Что:** ESLint + Prettier, Vitest (unit), Playwright (e2e smoke), скрипты `lint|typecheck|test|test:e2e`.
**Зачем:** правило №1 — не ломать работающее: без тестов оно не соблюдается.
**Почему так:** Vitest быстрее и проще Jest в этом стеке; Playwright — один инструмент для e2e и скриншотов дизайна.
**Как:** конфиги, пример unit-теста, smoke «главная открывается и есть заголовок».
**Результат:** четыре команды зелёные локально.
**Тест-кейсы:**
1. `pnpm lint`, `pnpm typecheck`, `pnpm test`, `pnpm test:e2e` → все завершаются успешно.
2. Сломать тест намеренно → команда падает с понятным сообщением (затем вернуть).

### T-E1-03 · CI на GitHub Actions · `devops`
**Что:** workflow для PR в `dev`/`main`: install (с кешем), lint, typecheck, test, build, e2e smoke.
**Зачем:** красное не попадает в `dev`.
**Почему так:** бесплатно, рядом с кодом.
**Как:** `.github/workflows/ci.yml`; Playwright-браузеры кешируются; секретов не требует (внешние вызовы замоканы).
**Результат:** на PR видны проверки; красные блокируют мерж по правилу.
**Тест-кейсы:**
1. Открыть любой PR → во вкладке Checks есть зелёный прогон `ci`.
2. В тестовом PR добавить ошибку lint → проверка красная (затем закрыть PR).

### T-E1-04 · Конфигурация окружения · `backend` `devops`
**Что:** `src/env.ts` с Zod-валидацией переменных; разделение публичных и серверных; `.env.example` актуален.
**Зачем:** секреты не утекут в браузер, ошибки конфигурации видны сразу.
**Почему так:** падаем на старте с понятным текстом, а не странной ошибкой в рантайме.
**Как:** публичные — `NEXT_PUBLIC_*`; серверные — через модуль с `server-only`; тест на валидацию.
**Результат:** без обязательной переменной приложение сообщает, какой именно.
**Тест-кейсы:**
1. Удалить `NEXT_PUBLIC_SUPABASE_URL` из `.env.local` → `pnpm dev` выдаёт ошибку с названием переменной. Вернуть.
2. `grep -r SUPABASE_SECRET_KEY .next/static` после `pnpm build` → ничего не найдено.

### T-E1-05 · Клиенты Supabase и обновление сессии · `backend` `auth`
**Что:** `src/lib/supabase/{client,server,middleware}.ts` на `@supabase/ssr`; middleware обновляет сессию.

**Почему так:** серверные проверки через `getUser()`; один способ создавать клиент.
**Как:** по документации `@supabase/ssr` для App Router; без бизнес-логики.

**Тест-кейсы:**

2. В сетевой вкладке нет запросов с секретным ключом.
(Unit: фабрики клиентов с моками.)

### T-E1-06 · Миграции БД и типы · `db` `backend` · 🔴 нужны доступы владельца
**Что:** применить `supabase/migrations/*` к dev-проекту, настроить `pnpm db:push`, `pnpm db:types`, сгенерировать `src/types/database.ts`.
**Зачем:** схема, RLS и триггеры — фундамент всех следующих эпиков.
**Почему так:** миграции в репозитории — единственный источник схемы.
**Как:** `supabase link` + `db push` (нужны access token и пароль БД) **или** SQL Editor по инструкции `SETUP.md`; затем генерация типов. Если сеть недоступна — написать типы вручную по `DATA_MODEL.md`, отметить TODO и блокер.
**Результат:** в dev-проекте есть все таблицы, RLS включена, типы актуальны.
**Тест-кейсы (владелец, панель Supabase):**
1. Table Editor → есть таблицы `profiles`, `tournaments`, `seasons`, `clubs`, `season_clubs`, `tours`, `matches`, `predictions`, `season_standings`, `admin_bootstrap`, `profile_private`.
2. У каждой из этих таблиц включён RLS (в Table Editor нет предупреждения «RLS disabled»).
3. Storage → бакеты `avatars` и `club-logos` существуют.
4. Database → Functions: есть `is_admin`, `can_predict`, `grade_match`, `close_season`.

### T-E1-07 · Сервисный слой и внутренний API v1 (каркас) · `api` `backend`
**Что:** структура по `docs/API.md`: обёртка `withApi`, формат ответов `{data,meta}`, ошибки `problem+json`, заголовки, `GET /api/v1/health`, `/version`, `/openapi.json`, снимок `docs/api/openapi.v1.json`, `pnpm api:openapi`.
**Зачем:** контракт с первого дня; все следующие фичи пойдут через него.
**Почему так:** версия в пути, сервисы отдельно от handlers — чтобы менять внутренности, не ломая клиентов.
**Как:** Zod-схемы → OpenAPI; contract-тесты; неизвестная версия → `404 api.version_unsupported`.
**Результат:** три служебных эндпоинта работают и покрыты тестами.
**Тест-кейсы:**
1. `curl localhost:3000/api/v1/health` → `200`, в теле `data.status = "ok"`, заголовки `X-Request-Id` и `API-Version: 1`.
2. `curl localhost:3000/api/v1/version` → версия приложения (из `package.json`) и список поддерживаемых версий API `["v1"]`.
3. `curl -i localhost:3000/api/v9/health` → `404`, `Content-Type: application/problem+json`, `code: api.version_unsupported`.
4. `curl localhost:3000/api/v1/openapi.json` → валидный JSON, содержит три пути.
5. `curl -i localhost:3000/api/v1/nope` → `404 problem+json`.

### T-E1-08 · Тема и токены · `frontend` `design`
**Что:** токены цвета, шрифтов, радиусов, отступов (Tailwind theme + CSS variables) по `docs/DESIGN.md`; шрифты через `next/font` (кириллица).

**Результат:** токены описаны в коде и в `docs/design/README.md`.
**Тест-кейсы:**

2. Заголовки отображаются узким капсом, кириллица без «тофу».

### T-E1-09 · Базовые UI-компоненты · `frontend` `design`
**Что:** Button (primary/secondary/text), Input/Label/FieldError, Card, Badge (точный счёт/исход/мимо), Table (базовая), Container, Skeleton.
**Зачем:** единый вид и скорость следующих экранов.
**Почему так:** маленькая библиотека на токенах, без тяжёлых UI-фреймворков.
**Как:** доступность (фокус, aria, цель касания ≥ 44 px), варианты через props.
**Результат:** компоненты используются на `/styleguide`, покрыты unit-тестами на рендер и состояния.
**Тест-кейсы:**
1. На `/styleguide` видны все компоненты и их состояния (обычное, hover, focus, disabled, ошибка).
2. Табом по странице проходится фокус, он хорошо виден.
3. На ширине 360 px ничего не вылезает за экран.

### T-E1-10 · Каркас сайта · `frontend`
**Что:** корневой layout, шапка (логотип, навигация — только существующие страницы), подвал (YouTube, Telegram, Instagram, TikTok), страницы 404 и ошибки, `src/messages/ru.ts`.
**Зачем:** единый каркас для всех будущих страниц.
**Почему так:** не показываем пункты меню несуществующих разделов.
**Как:** адаптив 360/768/1280; ссылки на соцсети из конфига (владелец уточняет URL в задаче «Анализ», если их нет в репозитории).
**Результат:** каркас работает и на телефоне, и на десктопе.
**Тест-кейсы:**
1. 360 px: шапка и подвал помещаются, меню удобно нажимать.
2. 1280 px: контейнер не шире ~1200 px, всё по центру.
3. Открыть несуществующий адрес → страница 404 с ссылкой на главную.
4. Все тексты интерфейса — на русском, без «сырых» ключей.

### T-E2-01 · Сервис и API видео YouTube · `api` `backend`
**Что:** определить ID канала `@da_zby`, получать последние видео из RSS, исключать Shorts, кеш 1 час, запасной вариант при сбое; `GET /api/v1/videos?limit=6`.
**Зачем:** данные для главной и будущих клиентов.
**Почему так:** RSS не требует ключа API и квот; сервис отделён от страницы.
**Как:** `src/server/services/videos.ts` (парсинг, фильтр, кеш), DTO и схема v1, фикстура RSS в тестах, `YOUTUBE_CHANNEL_ID` в конфиге.
**Результат:** эндпоинт отдаёт видео в порядке «новое первым»; при недоступности YouTube отдаёт последний кеш, а без кеша — понятную ошибку.
**Тест-кейсы:**
1. `curl "localhost:3000/api/v1/videos?limit=6"` → 6 элементов, у каждого `id`, `title`, `publishedAt`, `thumbnailUrl`, `url`.
2. Среди элементов нет Shorts (сверить с каналом).
3. Первый элемент — самое новое видео канала.
4. `limit=0` и `limit=101` → `422 problem+json` с описанием поля.

### T-E2-02 · Блок видео на главной · `frontend`
**Что:** главная: крупный плеер с последним видео + сетка из 5 предыдущих; плеер подгружается по клику (превью → `youtube-nocookie.com`).
**Зачем:** главная ценность сайта для зрителя канала.
**Почему так:** ленивый плеер экономит трафик и ускоряет страницу на мобильных.
**Как:** данные — из сервиса напрямую (RSC), кеш 1 час; состояния загрузки/ошибки; адаптив.
**Результат:** главная показывает видео, клики открывают плеер/видео.
**Тест-кейсы:**
1. Главная показывает последнее видео и 5 предыдущих, названия совпадают с каналом.
2. Клик по превью крупного видео → запускается встроенный плеер.
3. Клик по видео из сетки → переключается плеер на него (или открывается на YouTube — по описанию в задаче).
4. 360 px: сетка в 1–2 колонки, без горизонтального скролла.
5. Отключить интернет/недоступен YouTube (имитация в dev) → страница не падает, показан запасной блок со ссылкой на канал.

### T-E2-03 · SEO-база и бренд-ассеты · `frontend`
**Что:** `metadata`, Open Graph/Twitter-карточка, favicon и иконки из `docs/design/logo.png`, `sitemap.xml`, `robots.txt`, `lang="ru"`.
**Зачем:** красивые превью при отправке ссылки в Telegram/соцсети и базовая индексация.
**Почему так:** почти весь трафик — по ссылкам из соцсетей.
**Как:** OG-картинка 1200×630 (логотип на чёрном/жёлтом), если нет SVG — из PNG.
**Результат:** ссылка на сайт выглядит аккуратно в мессенджерах.
**Тест-кейсы:**
1. Вкладка браузера показывает favicon и заголовок «Да забей».
2. `/sitemap.xml` и `/robots.txt` открываются.
3. Вставить ссылку в Telegram (после выкладки/через временный туннель) → превью с картинкой и описанием; либо проверить теги через «просмотр кода страницы».
4. Mobile Lighthouse/PageSpeed: Performance не ниже ~85, Accessibility не ниже 90 (ориентир, не догма).
