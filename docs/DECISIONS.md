## Продукт и правила

**D-001 · 2026-10-24 · ✅ Дедлайн прогнозов — на весь тур, за 10 минут до начала первого матча.**
Причина: простое понятное правило для участников. Реализация: `tour_deadline()` в БД; админ может закрепить вручную (`deadline_override`).

**D-002 · 2026-10-24 · ✅ Очки: точный счёт 3, верный исход 1, ошибка 0; настраивается в турнире.**

**D-003 · 2026-10-24 · ✅ Учитывается итоговый счёт с учётом доп. времени, без пенальти.** Серию пенальти пока не заводим.

**D-004 · 2026-10-24 · ✅ Перенос/отмена матча.** Очки считаются только после того, как админ внёс результат; отменённые матчи исключаются.

**D-005 · 2026-10-24 · ✅ Чужие прогнозы видны всегда; данные для общего просмотра обновляются раз в 30 минут (кеш).**
Риск: до дедлайна можно подсмотреть чужие прогнозы (через сайт или API). Если понадобится — одна политика в БД скроет прогнозы до дедлайна тура.

**D-006 · 2026-10-24 · ✅ Сортировка рейтинга:** очки → точные счета → угаданные исходы; при полном равенстве — одинаковое место (дата регистрации не учитывается).

**D-007 · 2026-10-24 · ✅ Конец сезона:** админ закрывает сезон — итоговые места фиксируются в профилях; закрытие можно откатить.

**D-008 · 2026-10-24 · ✅ Туры заполняются только вручную** (автозагрузка из API — вне объёма).

**D-009 · 2026-10-24 · ❓ «Победа» = точный счёт или верный исход; «поражение» = неверный прогноз; % побед = победы ÷ (победы + поражения).** Владелец просил «полные названия», определения зафиксированы в глоссарии `PRODUCT.md`. Подтвердить.

**D-010 · 2026-10-24 · ❓ Не сделанный прогноз не считается ни прогнозом, ни поражением.** Подтвердить.

## Решения запуска 0.1.0

**D-041 · 2026-10-24 · 🛠 Next.js 16 с Cache Components** (шаблон create-next-app по умолчанию: `cacheComponents`, `partialPrefetching`). Кеш данных — `'use cache'` + `cacheLife` вместо `revalidate`. Причина: актуальная модель кеша Next.js; старая будет удалена в следующей мажорной версии. DAZBY-10.

**D-042 · 2026-10-24 · 🛠 Временные соответствия Jira (статусы заменены D-049)** до настройки проекта владельцем: эпик = «Рабочий процесс»; Анализ/Баг = «Задача» + метка `analysis`/`bug`; «Тестирование» = «В работе» + метка `testing`; «Бэклог» = «К выполнению» + метка `backlog`. DAZBY-1.

**D-043 · 2026-10-24 · 🛠 (заменено 24.10.2026: после `gh auth login` — обычные PR) Пока не выполнен `gh auth login`, задачи вливаются в `dev` локальным squash-мержем** (описание PR с «Риском регресса» — в сообщении коммита), проверки прогоняются локально. После входа — обычные PR. DAZBY-1.

**D-044 · 2026-10-24 · 🛠 OpenAPI строится из Zod 4 встроенным `z.toJSONSchema()`** (OpenAPI 3.1 = JSON Schema 2020-12), без библиотек вроде zod-to-openapi; эндпоинты описаны в одном реестре (`endpoints.ts`), из которого читают и handlers, и OpenAPI. Скрипт снимка запускается через `tsx` (dev-зависимость). Причина: ноль новых рантайм-зависимостей, контракт не расходится с кодом. DAZBY-16.

**D-045 · 2026-10-24 · 🛠 Видео — из RSS плейлиста длинных видео `UULF<id без UC>`, запасной вариант — RSS канала без Shorts.** Причина: в фиде канала 13 из 15 последних записей — Shorts (проверено 24.10.2026), из него не набрать 6 обычных видео. Риск: `UULF` не документирован YouTube; при поломке сработает запасной фид (видео будет меньше), а тест-кейсы главной это покажут. Кеш — в памяти процесса (1 ч) с отдачей последнего удачного списка при сбое: так поведение одинаково для страницы и API и не зависит от модели кеша Next. DAZBY-21.

**D-046 · 2026-10-24 · ✅ Ручная проверка — только ключевая, остальное — автотесты.** Решение владельца: стремиться к максимальной автоматизации разработки; ключевые решения остаются за владельцем. Задачу, у которой все тест-кейсы автоматизированы (🤖) и CI зелёный, Claude закрывает сам; владельцу остаются 🔑-кейсы (ключевые экраны, реальные внешние интеграции, права на живых данных, необратимые действия). Заменяет правило «в Готово переводит только владелец» (D-030 в этой части). DAZBY-38.

**D-047 · 2026-10-24 · ✅ Миграции к dev-Supabase применяет GitHub Actions (`db-migrate`) при мерже в `dev`.** Решение владельца (DAZBY-39): секреты `SUPABASE_ACCESS_TOKEN`/`SUPABASE_DB_PASSWORD` хранятся в GitHub, Claude их не видит; миграции попадают в БД только через PR и зелёный CI; CI запрещает править существующие миграции. Прямой доступ Claude к БД (MCP) не используется. Прод — отдельным workflow с ручным подтверждением (E8). DAZBY-40.

**D-048 · 2026-10-24 · 🛠 Тестовый стенд Railway (ветка dev) проверяется автоматически:** после каждого успешного деплоя workflow `stand-check` гоняет health и весь e2e по `https://dazby-production.up.railway.app`. Адрес сайта на Railway берётся из `RAILWAY_PUBLIC_DOMAIN`, значение без схемы нормализуется (инцидент: голый хост в `NEXT_PUBLIC_SITE_URL` ронял запуск). Диагностика падений — Railway Project Token в `.env.local` (`RAILWAY_TOKEN`). DAZBY-42.

**D-049 · 2026-10-24 · 🛠 Статусы «Бэклог» и «Тестирование» созданы в Jira через REST API** (`POST /statuses` с областью PROJECT + `POST /workflows/update`; для team-managed проекта это работает, валидацию даёт `/workflows/update/validation`). Метки `backlog`/`testing` заменены статусами; D-042 в части статусов заменено. Тип «Анализ» через API не создан — остаётся метка `analysis`. Копия workflow до изменения — локально, откат возможен.
