# AUTOPILOT — регламент автономного запуска

Этот файл — твоя инструкция на весь запуск. Подчиняется `CLAUDE.md` (если есть конфликт — прав `CLAUDE.md`). Сопроводительное сообщение владельца может переопределить параметры ниже.

## 0. Параметры запуска

| Параметр | Значение по умолчанию |
|---|---|
| Цель запуска | Релиз **0.1.0** (эпики E1 «Фундамент» и E2 «Главная и видео») |
| Режим | Без остановок между задачами; без ожидания одобрений по ходу |
| Мердж в `dev` | Сам, когда проверки зелёные |
| Статус «Готово» | Не ставишь никогда: после твоей работы задача — «Тестирование»; в «Готово» переводит владелец после ручных тест-кейсов |
| Ключевые решения | Только с согласованием (`CLAUDE.md`); независимое от них продолжай |
| Завершение | Достиг цели → итоговая сводка (раздел 7) → **стоп** |

## 1. Подготовка (фаза 0)

1. Определи, где работаешь (локальная машина владельца или облачная песочница). Запомни ограничения: в песочнице сеть обычно ограничена реестрами пакетов и GitHub — Supabase, Jira и YouTube могут быть недоступны из shell (тогда используй MCP-инструменты, а то, что нельзя, оформляй как блокер владельцу).
2. Репозиторий `https://github.com/Readberg/da_zby.git`: если не склонирован — клонируй (в песочнице — через инструмент подключения репозитория). Распакуй комплект из архива в корень репозитория, **не затирая** существующие файлы без проверки (при конфликте — остановись и спроси).
3. Прочитай целиком: `CLAUDE.md`, `docs/*`, `docs/tasks/E1-E2.md`, `supabase/migrations/*`, `docs/STATUS.md`. Если `STATUS.md` содержит прогресс прошлого запуска — продолжай с него, а не с нуля.
4. Проверь инструменты и доступы, **не выводя секреты**: git и права на push, `gh`, node ≥ 20, pnpm (установи через corepack), Supabase CLI, Atlassian MCP (получи `cloudId`, найди проект DAZBY), наличие `.env.local`.
5. Убедись, что есть ветки `main` и `dev` (создай `dev` от `main`; комплект первым коммитом — в `main`, затем `dev` от него).
6. `.env.local` создай из `.env.example` (секреты оставь пустыми, их вносит владелец).

## 2. Чек-лист для владельца (фаза 1) — до основной работы

Сразу после проверки доступов, **до начала разработки**:

1. Составь для владельца сообщение «ЧТО НУЖНО СДЕЛАТЬ ВАМ» на основе `docs/SETUP.md`. Включай только то, чего реально не хватает (по результатам проверки), в порядке приоритета:
   - 🔴 блокирует работу сейчас (доступ к Jira, Supabase, GitHub);
   - 🟡 понадобится в следующих эпиках (Google-вход, SMTP);
   - 🟢 в самом конце (Railway, домен, прод).
2. Для каждого пункта: зачем нужно · что без этого заблокировано · **пошаговая инструкция** (куда зайти, что нажать, что скопировать, куда вставить — пути копируй из `SETUP.md`, уточняя по реальному интерфейсу) · как проверить, что получилось. Секреты владелец вносит сам в `.env.local`; в чат и файлы их просить не нужно.
3. Отправь это сообщение владельцу сразу (SendUserMessage/ответ в чат), продублируй в Jira задачей «Доступы и настройки владельца» (метка `devops`, чек-лист в описании, статус «К выполнению»).
4. **Не жди ответа.** Продолжай всё, что не зависит от этих шагов. Заблокированные задачи помечай `⛔ Блокер` и берись за следующие. Когда блокер снят (владелец ответил/появился доступ) — вернись к ним.

## 3. Jira (фаза 2)

- Проверь типы Эпик/Задача/Баг/Анализ и статусы по `WORKFLOW.md`. Чего нет — добавь, если позволяют права; иначе — пункт в чек-лист владельца и временно используй ближайший тип с меткой.
- Создай эпики E1–E8 (`docs/ROADMAP.md`).
- Создай задачи **ровно по `docs/tasks/E1-E2.md`** (текст, метки, тест-кейсы переносишь как есть, уточняя по реальности). Статус «К выполнению», родитель — эпик.
- Идеи из «Идеи в Бэклоге» заведи как «Анализ» в «Бэклог».
- Если Jira недоступна — веди учёт в `docs/STATUS.md` и синхронизируй, как только доступ появится. Не останавливай разработку.

## 4. Цикл по задаче (фаза 3)

Порядок — по зависимостям из каталога. Для каждой задачи:

1. Проверь блокеры. Заблокирована — `⛔ Блокер` и следующая.
2. Jira: «В работе» + комментарий `▶ Старт`.
3. Ветка `feat|fix|chore|docs/DAZBY-<N>-<slug>` от свежего `dev`.
4. Если трогаешь существующее поведение — сначала тесты на текущее поведение (правило №1).
5. Реализуй минимально необходимое по критериям «Результат». Без расширения объёма.
6. Тесты: unit/contract/e2e по задаче. Внешние вызовы (YouTube, Supabase) в тестах — моки/фикстуры.
7. Доки: обнови то, что изменилось (`DATA_MODEL`, `API`, `DESIGN/design`, `DECISIONS`, при необходимости `PRODUCT`).
8. Полная проверка: `pnpm lint && pnpm typecheck && pnpm test && pnpm build` (+ e2e smoke там, где есть). Красное — чини. **3 неудачные попытки подряд** по одной причине → `⛔ Блокер` с описанием в Jira, переходи к следующей.
9. Коммиты — Conventional Commits, англ., ключ задачи. PR в `dev` с описанием: что и зачем · как проверить · **Риск регресса** · миграции/доки. Смержи сам (squash), удали ветку.
10. Jira: проверь, что в описании есть **тест-кейсы для ручной проверки** (если нет или устарели — перепиши под реальный результат: предусловия → шаги → ожидаемое), добавь `✔ Сделано` (1–3 пункта + PR) и переведи в «Тестирование».
11. Обнови `docs/STATUS.md` (задача, статус, PR, блокеры, вопросы).
12. Дальше — следующая задача. Не останавливайся для промежуточных отчётов.

Побочные находки (идея, чужой баг, техдолг) → отдельная задача «Анализ» или «Баг» в «Бэклог». Текущую работу не расширяй.

## 5. Релиз (фаза 4)

Когда все задачи E1/E2 дошли до «Тестирование» (кроме заблокированных владельцем):
1. Чек-лист релиза из `WORKFLOW.md`: `CHANGELOG.md`, версия `0.1.0` в `package.json`, актуальность доков.
2. PR `dev` → `main`, мерж, тег `v0.1.0`, GitHub Release с текстом из CHANGELOG.
3. Если критичная задача заблокирована так, что релиз был бы ложным (например, не применена миграция, и страница не работает) — релиз не выпускай, объясни в сводке.
4. Релиз ≠ приёмка: ручное тестирование владельцем продолжается; найденные баги пойдут в `0.1.x`.

## 6. Стоп-условия и запреты

- Никогда: force-push, прямые коммиты в `main` (кроме релизного мержа), удаление задач/веток чужой работы, `drop`/разрушающие миграции, изменение или вывод секретов, коммит секретов, любые действия с продом.
- Не меняй утверждённые правила (`PRODUCT.md`, `DECISIONS.md` со статусом ✅) без согласования.
- Не добавляй функциональность вне каталога задач.
- Остановись и спроси владельца, если: конфликт при распаковке комплекта; неясно, кому принадлежит найденный в репозитории код; действие необратимо.

## 7. Итоговая сводка (фаза 5) — формат обязателен

Отправь владельцу (и сохрани в `docs/STATUS.md`):

1. **Итог**: что достигнуто (версия, что работает), 2–4 строки.
2. **К ручному тестированию**: таблица «ключ · название · что проверить в двух словах · порядок». Порядок — от основы к деталям (сначала запускается ли проект, потом главная, потом остальное). Полные тест-кейсы — в самих задачах Jira.
3. **Заблокировано и нужно от вас**: список с шагами (что сделать → какие задачи разблокируются).
4. **Ключевые решения на согласование**: по каждому — варианты, рекомендация, цена; ссылка на задачу «Анализ».
5. **Честная оценка** (стиль `ADVISOR.md`): что слабое, где вы недооцениваете объём или риск, что проверить в первую очередь, чего мы не знаем (нет данных) и как узнать.
6. **Что дальше**: готовая фраза для следующего запуска (например, «продолжай до 0.2.0») и ожидаемый объём.

## 8. Возобновление

Если сессия прервалась: прочитай `docs/STATUS.md` и в Jira все задачи «В работе», проверь незакрытые ветки и PR, продолжи с того места. Не дублируй уже созданные эпики и задачи — ищи по названию.
